# No Repeat Skill

把值得复用的做法变成 Agent 可稳定执行的能力，同时避免把一次性任务包装成过度复杂的 Skill。

## 核心约定

- 真实目标优先于用户预设的工具、格式和步骤。
- 先选正确的载体，再写 Skill；不用 Skill 代替更合适的文档、模板或脚本。
- 结构随风险、复杂度和复用范围增长，不默认生成空目录或治理文件。
- 实际行为证据优先于文件数量、表格完整度和自我声明。
- 不伪造测试、用户反馈、发布状态或外部兼容性。
- 保留用户范围和授权边界；发布、上传、付费、删除和生产环境修改不因使用本 Skill 而自动获得授权。

## 从哪里开始

1. 检查用户提供的流程、样例、现有 Skill、项目规则和目标平台；可直接读取的信息不要反问用户。
2. 用一句话重写真实目标，并标出用户方案中尚未证明的假设。
3. 阅读 [载体决策与范围](references/decision-and-scope.md)，选择最小充分载体。
4. 只有结论是“建立或修订 Skill”时，才继续下面的构建流程。

信息不足时，先完成不依赖该信息的读取和分析。只询问会改变载体、权限、目标平台或验收结论的问题；其余使用可逆、明示的假设继续。

## 构建流程

### 1. 建立行为合同

先定义：

- 谁会用，用户会如何表达需求。
- 哪些请求应该触发，哪些近似请求不应触发。
- 输入、最终产物和可观察的合格标准。
- 需要人工判断、最新信息、外部工具或额外授权的节点。

需要详细的路由、描述和目录设计时，阅读 [设计与构建](references/design-and-build.md)。

### 2. 选择最小可行结构

从仅含 `SKILL.md` 开始，只在下列条件成立时增加资源：

- 只有部分场景需要的长知识：`references/`。
- 可重复、可确定执行的检查或转换：`scripts/`。
- 需要复制或改造为用户产物的模板或静态文件：`assets/`。
- 目标平台需要的界面、路由或元数据：平台对应文件。

每个资源都必须改变 Agent 的决策、行为或产物；否则删除。

### 3. 实现

- `description` 详细说清能力、触发语境和重要排除项，但不把全部流程塞进去。
- `SKILL.md` 保留共用决策、必要顺序、安全边界和按需导航。
- 已有项目中只修改必要文件，保留用户的无关改动。
- 复刻或重写第三方 Skill 时，先检查许可证；不得通过删除姓名或品牌来规避保留通知、归属或二次分发条件。

### 4. 验证

阅读 [测试与迭代](references/testing-and-iteration.md)，按风险递增检查：

1. 结构：名称、frontmatter、资源链接、占位符。
2. 执行：新增脚本能运行，产物能打开，高风险动作有明确停止点。
3. 路由：典型正例、明确反例和容易混淆的近邻场景。
4. 行为：在真实或高保真请求中产出合格结果。
5. 回归：修复新失败后，重跑受影响的旧场景。

可用以下命令做通用静态检查：

```bash
python3 scripts/validate_skill.py <skill-directory>
```

这个脚本只检查文件和明显风险，不能证明 Agent 真的会在正确时机触发或产出好结果。

### 5. 发布与交付

当任务涉及第三方来源、公开仓库、外部依赖、密钥、用户数据或高风险动作时，必须先阅读 [安全与发布](references/safety-and-release.md)。需要跨平台分发时，再阅读 [平台适配](references/platform-compatibility.md)。

交付时先给结论，再简要说明：

- 最终选择了什么载体，为什么。
- 新建或修改了哪些有用部分。
- 实际运行了哪些验证，结果如何。
- 哪些结论仍只是推断，还需要真实使用证据。
- 剩余风险、阻塞或后续迭代触发条件。

## 附带模板

只在有对应产物时使用：

## 常见失败

- 用“以后可能复用”代替真实复用证据。
- 把整份教程、项目说明或业务知识原样塞入 `SKILL.md`。
- 强制每个 Skill 都拥有模板、脚本、案例、测试库和版本治理。
- 把 JSON 格式通过、关键词命中或自评报告当成真实 Agent 行为测试。
- 只测“应该触发”，不测“不应该触发”和“应该由其他能力处理”。
- 为了显得完整而伪造案例、测试结果、兼容性或成熟度。
- 复刻第三方作品时只替换名称和标识，却保留受限制的表达、代码或资产。
