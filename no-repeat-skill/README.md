# No Repeat Skill

**把反复解释的做法，变成 Agent 能稳定复用的能力。**

`no-repeat-skill` 用于将重复工作流、SOP、长提示词、团队经验、专家方法和现有 Agent Skill，转化为精简、可安装、可执行、可验证、可迭代的 Skill 能力包。

它不会默认“用户说要做 Skill，就立刻创建一套复杂目录”。它会先用第一性原理检查真实目标，然后在一次性回答、文档、项目规则、记忆、模板、脚本、自动化和 Skill 之间，选择成本最低且足以解决问题的载体。

## 它解决什么问题

当人们开始高频使用 Agent，常会出现以下情况：

- 同一类任务，每次都要重新解释步骤。
- 已经有 SOP 或长提示词，但 Agent 仍会遗漏关键判断。
- 一段提示词越写越长，触发边界和资源使用反而越来越混乱。
- 已经建立 Skill，但经常误触发、不触发或产物不稳定。
- 文件看上去很完整，却没有真正运行过的验证。
- 为了“产品化”而增加大量模板、治理文件和测试空壳，维护成本超过收益。
- 复刻第三方 Skill 时只替换名称，忽略许可、归属和重新分发条件。

No Repeat Skill 要解决的不是“怎样写一份更长的提示词”，而是“如何把值得复用的经验，变成 Agent 能在正确场景下稳定执行的能力”。

## 核心能力

### 1. 判断是否真的需要 Skill

先检查重复频率、失败成本、判断复杂度、可验证性和维护成本。如果文档、模板或脚本更合适，就不强行建立 Skill。

### 2. 从真实目标重新设计

分离用户想得到的结果与用户已经想到的方法，检查“必须用这个工具”、“必须按旧 SOP 的顺序”、“文件越多越完整”等尚未证明的假设。

### 3. 设计准确的触发边界

同时定义：

- 应该触发的真实请求。
- 明确不应触发的请求。
- 表面相似，但应该交给其他 Skill、工具或普通执行的近邻请求。

### 4. 构建最小充分结构

默认从一份精简的 `SKILL.md` 开始。只当真实任务需要时，才增加：

- `references/`：只有部分场景需要的长知识。
- `scripts/`：需要稳定、可确定重复执行的检查或转换。
- `assets/`：会被复制或改造成最终产物的模板和静态素材。
- `agents/` 或其他元数据：目标平台真正需要的界面与调用配置。

### 5. 设计真实验证

它会明确区分：

- 文件存在、YAML 正确、JSON 可解析、链接不断开。
- Agent 会在正确的时机选择该 Skill。
- Agent 会按预期读取资源并执行工具。
- 真实任务产物满足验收标准。
- 修改新问题后，已经通过的能力没有回归。

这些证据层级不能互相替代。静态校验通过不等于 Agent 行为已被证明。

### 6. 处理发布与第三方风险

公开分发或复刻第三方能力时，检查：

- 许可证和重新分发条件。
- 必须保留的归属、声明和通知。
- 密钥、cookie、证书、本机路径和未脱敏数据。
- 网络、账号、付费服务和外部包依赖。
- 上传、发布、删除、付费和生产变更的授权边界。

## 什么时候应该使用

适合调用 No Repeat Skill 的请求：

- “把我每周都要重复解释的流程做成 Skill。”
- “这套 SOP 是应该做成 Skill、脚本、模板还是项目规则？”
- “把这段长提示词重构为可安装的 Agent Skill。”
- “这个 Skill 经常误触发，请审查并修好。”
- “给这个 Skill 补齐反例、近邻场景和端到端测试。”
- “检查这个 Skill 是否适合公开发布。”
- “把这个第三方 Skill 的有效方法重新设计成一个新能力包。”

## 什么时候不应该使用

以下请求应直接完成，不要启动 Skill 产品化流程：

- 单次改写、润色、翻译和格式转换。
- 简单事实查询或概念解释。
- 用户已经明确要求的一次性小修改。
- 核心问题只是定时或事件触发的自动化。
- 只适用于一个仓库的协作规则。
- 完全可由确定性程序处理的批量转换。
- 用户要解决的是商业、购买或技术决策，而不是创建 Skill。

## 第一性原理决策

在写任何文件前，先回答八个问题：

1. 用户最终想稳定获得什么结果？
2. 真正会重复的是哪一部分？
3. 每次输入会变，还是处理规则会变？
4. 哪些环节需要语境判断或专家经验？
5. 哪些环节可以用确定性脚本取代？
6. 没有额外指导时，Agent 通常会在哪里失败？
7. 怎样从最终结果中判定是否成功？
8. 什么情况不应执行，什么动作需要额外授权？

详细方法见 [载体决策与范围](references/decision-and-scope.md)。

## 载体选择

| 需求本质 | 更合适的载体 |
| --- | --- |
| 只需完成这一次 | 直接执行 |
| 需要人长期查阅的稳定知识 | 文档 |
| 单一项目中的固定规则 | 项目规则文件 |
| 个人长期偏好 | 记忆或用户配置 |
| 反复使用的固定格式 | 模板 |
| 输入到输出完全可明确编码 | 脚本或小工具 |
| 定时、监控或事件触发 | 自动化 |
| 需要意图识别、上下文判断、多步执行和按需资源 | Agent Skill |

这些载体可以组合。例如，Skill 负责判断和调用，脚本负责确定性处理，模板负责最终格式。

## 支持的三种工作模式

### 从零创建

从真实任务、失败点和验收条件出发，确定最小可行结构，再实现并验证。

### 重构现有 Skill

保留可追溯基线，用真实失败定位是路由、指令、知识、工具还是权限问题，只修改与根因直接相关的部分。

### 审查与发布验收

检查触发边界、资源可发现性、脚本可执行性、证据强度、隐私、许可和发布副作用，给出可交付、有条件交付或不可交付的明确结论。

## 完整工作流

```text
读取真实材料
    ↓
重定义真实目标
    ↓
检查隐藏假设与替代载体
    ↓
决定不做 Skill / 创建 Skill / 修订 Skill
    ↓
定义触发、反触发、近邻和验收条件
    ↓
创建最小充分结构
    ↓
运行结构、脚本、路由和端到端验证
    ↓
审查安全、许可和发布边界
    ↓
结论先行交付，明示证据限制和剩余风险
```

## 安装

### 方式一：克隆仓库

```bash
git clone https://github.com/GodAI-Master/GodSkill.git
```

将完整的 `no-repeat-skill/` 目录复制到你使用的 Agent skills 目录。不要只复制 `SKILL.md`，否则参考文件、模板和校验脚本会丢失。

### 方式二：下载单个目录

从 GitHub 下载仓库 ZIP，解压后仅取出 `no-repeat-skill/` 完整目录，再放入目标 Agent 的 skills 目录。

### 平台注意事项

- 目标环境应能读取 `SKILL.md` 及相对路径资源。
- Codex 界面元数据位于 `agents/openai.yaml`。
- 其他平台可能需要调整元数据字段，但不应改变核心行为边界。
- 没有实际安装测试时，只能说“结构可携带”，不应宣称已经完全兼容。

## 使用方式

### 判断是否应该做 Skill

```text
Use $no-repeat-skill 分析这套客户周报流程是应该做成 Skill、模板还是脚本。如果不值得做 Skill，请明确说明。
```

### 从零创建

```text
Use $no-repeat-skill 把我每周都要重复执行的客户会议复盘流程做成一个可安装的 Agent Skill。请直接建立文件、运行检查，并说明哪些行为尚未得到真实验证。
```

### 重构现有 Skill

```text
Use $no-repeat-skill 审查这个现有 Skill。重点检查详细简介是否误触发、入口是否过长、参考文件是否无法发现，然后做最小修复并跑回归检查。
```

### 公开发布前审查

```text
Use $no-repeat-skill 检查这个 Skill 是否可以公开发布。请检查许可、第三方内容、私有路径、密钥、依赖、内部链接和已声称的测试证据。
```

## 交付结果

正常交付应当先告诉用户结论，再说明：

1. 最终选择了什么载体，为什么。
2. 新建或修改了哪些真正有用的部分。
3. 实际运行了什么检查，结果如何。
4. 哪些结论只有静态证据，尚未经过真实 Agent 行为测试。
5. 剩余风险、阻塞和下一次应该迭代的触发条件。

## 验证

在 `no-repeat-skill/` 目录内运行：

```bash
python3 scripts/validate_skill.py . --strict
```

它会检查：

- Skill 名称和目录名是否一致。
- `SKILL.md` 的 frontmatter 和详细简介是否合法。
- Markdown 内部链接是否断开或越出 Skill 目录。
- JSON 是否能够解析。
- 路由语料是否同时包含正例、反例和近邻例。
- 是否遗留占位符、本机私有路径、明显密钥或发布垃圾文件。
- 支持资源是否可以从包内 Markdown 找到。

这是静态检查器。它不会调用模型，也不能证明 Agent 真的会在正确时机选择 Skill 或产出合格结果。真实行为验证方法见 [测试与迭代](references/testing-and-iteration.md)。

## 相比常见 Meta Skill 的改进

### 不强制固定的重型交付物

不要求每个 Skill 都必须包含完整案例库、治理文件、发布清单、多种模板和多个脚本。只当文件会改变 Agent 的决策、行为或产物时才保留。

### 先选载体，再建包

将“不做 Skill”、“先完成一次真实任务”和“改用脚本或模板”都作为合法结论，避免对尚未稳定的流程过早产品化。

### 经验证据不等于可观察证据

不把文件数量、模板完整度、JSON 格式通过和 Agent 自我评价当成真实能力证明。

### 允许不同风险使用不同深度

个人草案、团队共用、公开分发和高风险生产能力使用不同验收深度，不用同一套最重标准处理所有任务。

### 将许可与去标识化分开

删除原作者名称和品牌不会自动消除原作许可要求。如果不应该复制原文、代码或模板，就只保留通用问题和可验证目标，独立重新设计具体内容。

## 常见问题

### 它只是一段很长的提示词吗？

不是。`SKILL.md` 是 Agent 入口，整个能力还包括按需知识、模板、确定性校验脚本和路由语料。

### 为什么不是所有重复工作都做成 Skill？

因为有些重复工作只需要一个模板，有些完全可以用脚本稳定处理，有些只是单个项目的规则。Skill 带来路由、资源和维护成本，必须证明这些成本值得。

### 必须先有大量真实案例才能开始吗？

不是。可以先建立明确标注为未验证的个人草案。但没有真实使用证据时，不应宣称它已经成熟、稳定或适合组织级发布。

### 校验脚本通过后就可以发布吗？

不一定。校验脚本只能证明基本结构、内部链接和明显风险没有问题。公开发布还需要许可审查、新环境安装测试和真实行为证据。

### 可以用它复刻别人的 Skill 吗？

可以用它分析和重新设计同类能力，但必须先检查原作许可条件。若不得直接复制受保护内容，就独立重写文字、结构、代码、模板和测试，而不是只替换名称。
