# 设计与构建

## 使用时机

当结论已经是建立或重构 Skill，需要设计名称、`description`、路由边界、目录、资源和执行约束时读取。

## 先写行为合同

在创建文件前，写出以下内容：

- **意图**：用户想完成的工作，不是某个固定关键词。
- **正例**：3–5 条真实说法，覆盖直接请求和隐含请求。
- **反例**：明确不应触发的请求。
- **近邻**：语义相近，但应该由普通执行、另一个 Skill 或工具处理的请求。
- **产物**：文件、修改、分析、可运行输出或决策。
- **验收**：能够从结果中观察的必要条件。
- **停止点**：需要用户选择、授权或外部状态变化才能继续的地方。

## 名称与 description

### 名称

- 使用小写字母、数字和连字符。
- 名称表达稳定能力，不绑定一次性项目、客户或活动。
- 避免“全能”、“大师”、“终极”等无法改善路由的修饰词。

### description

`description` 是选择器，需要在 Skill 未被读取前就能帮助 Agent 判断是否适用。它应包含：

1. 该 Skill 实际能做什么。
2. 用户可能使用的任务语境和对象。
3. 会改变路由结果的关键条件。
4. 一两个容易误触发的排除项。

不要在 `description` 中重复全部流程或营销口号。长度以能消除路由歧义为准，不追求越长越好。

## SKILL.md 的信息密度

入口文件应使 Agent 在不读全部附件的情况下做出第一个正确决定。保留：

- 目标与必要约束。
- 需要顺序的关键步骤。
- 何时读哪个参考文件。
- 容易产生实际伤害的禁止项。
- 可执行的验证方式。

移出：

- 只有某个模式才需要的长流程。
- 完整 API、schema、业务规则和大量案例。
- 不改变行为的背景历史、口号和重复说明。

## 资源设计

### references

每个参考文件都应有一个明确主题和加载条件。在 `SKILL.md` 中直接链接，并说明何时读取。避免一个超大“手册”文件。

### scripts

只在同一逻辑会反复编写、确定性对正确性重要，或手工操作极易出错时添加脚本。脚本应：

- 默认无破坏性。
- 对输入和输出路径有明确规则。
- 错误时返回非零状态并给出可理解信息。
- 尽量不依赖未声明的外部包。
- 实际运行过典型输入和失败输入。

### assets

仅放最终产物会复制或改造的模板、图标、样式、样例数据或起始文件。不把说明文档伪装成 asset。

## 规则的写法

将抽象形容词转换为可检查行为：

| 含糊要求 | 可执行表达 |
| --- | --- |
| 要专业 | 给出结论、依据和不确定性，不伪造数据 |
| 要安全 | 外部写入前解析目标，破坏性动作前取得明确授权 |
| 简洁一点 | 先输出不超过三条的结论，详细依据按需展开 |
| 自己检查 | 运行指定验证，记录命令、结果和未覆盖风险 |

## 修订现有 Skill

1. 保留一个未修改的基线快照或可追溯版本。
2. 查找一个真实失败，区分路由问题、指令问题、资源问题和工具问题。
3. 修改能直接影响该失败的最少文件。
4. 重跑该失败场景和受影响的旧场景。
5. 如果新规则只适用于一个特例，将它放到相应参考或测试中，不要污染全局指令。
