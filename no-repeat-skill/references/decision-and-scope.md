# 载体决策与范围

## 使用时机

当需要判断一套做法是否应该变成 Skill，或者需要在文档、模板、脚本、自动化和 Skill 之间选择时读取。

## 第一性原理拆解

不要从“如何把它写成 Skill”开始，先回答：

1. **结果**：用户真正想稳定获得什么结果？
2. **重复**：哪些部分会重复，频率和使用者范围如何？
3. **变化**：每次输入会变，还是处理规则会变？
4. **判断**：哪些节点依赖专家经验、上下文或取舍？
5. **确定性**：哪些步骤完全可由固定规则处理？
6. **失败**：无额外指导时，Agent 通常会遗漏、误触发或误判什么？
7. **验收**：如何从可观察结果中判定成功？
8. **边界**：什么情况不应执行，什么动作需要额外授权？

这八个答案比用户预设的文件树更重要。

## 选择最小充分载体

| 情况 | 首选载体 | 判断依据 |
| --- | --- | --- |
| 只需完成当前任务 | 直接执行 | 未来复用价值低 |
| 需要人阅读的稳定知识 | 文档 | 核心问题是查阅，不是 Agent 行为 |
| 单个项目内的固定规则 | 项目规则文件 | 不需要在多类请求中路由 |
| 个人的持久偏好 | 记忆或用户配置 | 是长期偏好，不是任务流程 |
| 固定格式反复复制 | 模板 | 复用的是容器，不是判断 |
| 输入到输出可完全明确编码 | 脚本或小工具 | 程序比 Agent 更可预测 |
| 需要定时、监控或事件触发 | 自动化 | 问题核心是调度 |
| 需要按意图路由、上下文判断、多步执行或按需资源 | Skill | Agent 需要在不同请求中稳定改变行为 |

载体可以组合。例如，Skill 负责判断和调用，脚本负责确定性转换，模板负责固定交付格式。组合应来自真实需要，不是为了展示完整。

## Skill 成立条件

不必机械打分。通常至少需要同时成立以下条件：

- 过去已经重复发生，或有高信心的近期复用计划。
- 没有 Skill 时存在稳定的遗漏、误判、反复解释或质量波动。
- 任务不只是确定性数据处理。
- 可以写出明确的触发语境和不触发语境。
- 有一种以上可观察的验收方式。
- 节省的解释成本、降低的失败成本或提升的一致性，值得后续维护。

如果只有假想用户和假想任务，建立探索性草案并标明未验证，不要声称为成熟能力。

## 成本与替代审查

在确定建立 Skill 前，至少比较：

- **更小**：一页项目规则或一个模板能否解决主要问题？
- **更稳**：哪些部分可改用脚本，避免模型随机性？
- **更久**：外部平台、接口或规则变更后，哪些知识会迅速失效？
- **更安全**：是否引入了原本不需要的网络、密钥或写操作？
- **从零设计**：如果不继承旧提示词的结构，现在还会用同样的分步和文件吗？
